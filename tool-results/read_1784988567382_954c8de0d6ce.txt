    29→# Turbopay — Comprehensive Research Report
    30→
    31→## 1. Project Overview
    32→
    33→**Turbopay** is a **consumer-facing Nigerian fintech web application** — a digital wallet + payments platform explicitly modelled on OPay, PalmPay, Kuda, Wise, and Revolut. The README tagline is *"The fast lane to your money."*
    34→
    35→- **Purpose:** Fund a wallet, transfer money (internal Turbopay ↔ Turbopay, and external to any Nigerian NUBAN bank account), buy airtime & data bundles, pay bills (electricity, cable TV, internet, water, Remita, Quickteller), request international transfers, hold multi-currency balances, issue virtual cards, run savings goals & investments, redeem vouchers, earn referrals/cashback rewards, raise and track disputes, and operate an admin compliance/risk console.
    36→- **Target users:** Everyday Nigerian consumers (with multi-country expansion to Ghana, Kenya, South Africa, UK). Two personas are surfaced in code: regular **Users** (default role `USER`) and **Admins** (`ADMIN`).
    37→- **Repository state:** Public GitHub repo `ifeanyiokomba/Turbopay`, TypeScript primary language, 0 stars at the time of research, last pushed 2026-07-25, current app version `0.3.0` per CHANGELOG. No license file committed at repo root (README claims MIT).
    38→- **Architecture summary (per README):** the codebase is divided into a deprecated `src/` payment-orchestration SDK and the canonical Next.js app `turbopay-complete-latest/`. The Next.js app is the single source of truth. A small `frontend/` directory holds a separate (older, mock-data) Next.js 14 admin/customer/merchant dashboard that is **not** the production UI.

    56→| Payments / KYC integrations | **Monnify** (virtual accounts + funding), **Paystack** (cards, transfers, identity, BVN, wallet, DVA), **Flutterwave** (v3 + v4), **Baxi** (bills/airtime), **Dojah** (KYC/NIN/BVN), **Onafriq**, **Quickteller (Interswitch)**, **Remita**, **Paga**, **MTN MoMo**, **Airtel Money**, **M-Pesa**, **Smartcash**, **Stripe** (cards + Identity + Issuing — feature-flagged), **Stripe.js** client (`@stripe/stripe-js` 9), **Wise** (international — recommended but sandboxed) |
    57→| Monitoring | **Sentry** Next.js SDK 10 (separate client/edge/server configs, sourcemaps, tree-shake debug logging) |
    58→| i18n | **next-intl** 4.3 — 5 locales (en, fr, sw, pt, ar) with RTL support for Arabic; messages in `src/messages/*.json` |
    59→| Themes | **next-themes** 0.4 (dark mode default) |
    60→| Toasts | **Sonner** 2 |
    61→| Carousel | **embla-carousel-react** |
    62→| Date | **date-fns** 4 + **react-day-picker** |
    63→| OTP input | **input-otp** |
    64→| Drawer | **vaul** |
    65→| Image cropper | Custom `cropper.tsx` part |
    66→| Tables | `@tanstack/react-table` |
    67→| Testing | **Vitest** 4 + `vitest.setup.ts`; ~28 test suites; CI uses real PostgreSQL 16 service container |
    68→| Build / deploy | Docker multi-stage (Bun → standalone Next.js output, ~130MB), `docker-compose.yml` with 3 app replicas + Postgres + Redis + Caddy, `vercel.json` cron (referenced), GitHub Actions CI, `render.yaml` (legacy SDK deploy), `k8s/cronjobs/turbopay-cron.yaml` |
    69→| Persistence (deprecated SDK) | In-memory `Map<>` + JSON files in `./data/` (per `src/utils/persistence.ts`) |

   183→## 4. Page / Route Inventory
   184→
   185→### 4.1 The SPA shell (`/`)
   186→A single Next.js page at `src/app/page.tsx` bootstraps the entire app. It calls `/api/auth/me` on mount, then renders one of:
   187→- **`<LoadingScreen />`** — premium animated splash (logo fade-rise + sheen sweep).
   188→- **`<LandingPage />`** — guest landing (hero, features, how-it-works, security/trust, why Turbopay, FAQ, testimonials, CTA, footer). Logged-out users see this.
   189→- **`<AuthScreen />`** — login/register modal (Tabs: Sign in / Create account, plus Forgot-password, MFA challenge, Email/SMS/WhatsApp verify dialogs, Google sign-in button).
   190→- **`<AppShell />`** — the authed SPA. Renders the active view from `useApp.view`. Has a left desktop sidebar, sticky top header (theme toggle, notifications bell, avatar dropdown), bottom mobile nav (Home / Wallet / Send / Bills / History), 15-min inactivity auto-logout with 2-min warning dialog, notifications panel (top-right), `<AiSupport />` floating chat widget, global PIN dialog provider.
   191→
   192→### 4.2 Non-authed public routes
   193→- `/` — bootstrap SPA
   194→- `/privacy` — privacy policy page
   195→- `/terms` — terms of service page
   196→- `/pay/[reference]` — public payment link landing (server component fetches `PaymentLink`, renders `<PaymentLinkClient />` for payment)
   197→- `/admin/login`, `/admin/forgot-password` — admin login / forgot-password (separate auth from user auth)
   198→- `/sentry-example-page` — Sentry test page

   204→3. `transfer` — Turbopay ↔ Turbopay / Bank / International tabs; recipient picker, bank BIN auto-detect from first 3 digits of account number, auto-resolve account name via `/api/banks/resolve`, transparent fee estimation via `/api/transfer/fee`, beneficiary save checkbox, PIN dialog → confirm → success card with reference + new balance.

   207→6. `history` — search + filter chips (All/Funding/Transfers/Airtime/Data/Bills), grouped-by-day transaction list, transaction detail dialog (reference, description, counterparty, provider, fee, date, status), CSV export via `/api/statements/generate`.
   208→7. `intl-transfers` — multi-currency wallet section, international beneficiary management (bank/SWIFT/routing/mobile wallet), FX quote dialog with fee breakdown, send flow with PIN, transfer tracking timeline (898-line view).

   210→9. `investments` — product catalog (FIXED_INCOME/MUTUAL_FUND/EQUITY/BOND/TBILL), portfolio summary (total value/principal/return), invest dialog with risk-level badges.
   211→10. `cards` (Virtual Cards) — list of card visualizations with gradient backgrounds (Visa/Mastercard), fund/withdraw/freeze/unfreeze/terminate, reveal PAN/CVV (audit-logged), spending controls, transactions list.
   212→11. `insights` — monthly in/out BarChart, category PieChart, top recipients, summary stats (avg tx, top category).

   214→**Account / growth**

   216→13. `beneficiaries` — saved recipients list, add/remove.
   217→14. `settings` — 1,520-line view: profile (avatar upload, full name, email, phone, bio, username), appearance (theme switch), notifications preferences, security (change password, set/change PIN, MFA setup/disable, NDPR data export, account deletion), locale switcher.

   301→## 6. Feature Inventory
   302→
   303→### Authentication & Sessions
   304→- Email/phone/username + password login (single identifier field, auto-detects type).
   305→- Registration with first/middle/last name, country (ISO 3166-1 alpha-2), username, email OR phone (at least one required), password (8+ chars, mixed case + digit), referral code, terms acceptance, verify channel (EMAIL/SMS/WHATSAPP).
   306→- **HaveIBeenPwned breach check** at registration (k-anonymity, fail-open).
   307→- **Per-user failed-login lockout** (5 fails → 15-min lock, defeats distributed-IP brute-force).
   308→- **Access + refresh tokens**: access 24h (HttpOnly cookie `tp_session`), refresh 30d (HttpOnly cookie `tp_refresh`, path-restricted to `/api/auth/refresh`).
   309→- **Iframe token**: short-lived (5-min) Bearer token for cross-site iframe contexts where third-party cookies are blocked. Stored only in page memory.
   310→- **WebAuthn passkeys** (`@simplewebauthn`): register / authenticate (both as second-factor and passwordless), per-device counter (cloning detection), transports, device type.
   311→- **TOTP MFA**: RFC 6238, 30s/SHA1/6-digit, replay prevention via `mfaLastStep`, 8 backup codes (scrypt-hashed + AES-encrypted blob), two-step setup (generate → prove).
   312→- **Google OAuth** (Google Identity Services via `<script src="https://accounts.google.com/gsi/client">`).
   313→- Session management UI: view active sessions, revoke any session, max 10 sessions per user.
   314→- **Auto-logout** at 15 min inactivity (2-min warning countdown).
   315→- Cross-tab refresh coordination via `BroadcastChannel`.

   317→### Wallet & Ledger
   318→- **Double-entry ledger** (`LedgerEntry`): DEBIT + CREDIT pair per movement, immutable, `balanceAfterKobo` per entry, `pairId` cross-link.
   319→- **Atomic conditional UPDATE** for debits (`WHERE balanceKobo >= amount AND status = 'ACTIVE'`) — no TOCTOU window.
   320→- **PostgreSQL advisory locks** (`pg_advisory_xact_lock(hashtext(userId))`) serialize concurrent debits per user.
   321→- **Optimistic concurrency** via `version` field on `Wallet`.
   322→- **Reconciliation**: `reconcileWallet()` recomputes balance from ledger via SQL aggregate, drift-corrects if needed.
   323→- **Multi-currency wallets** (`CurrencyWallet` + `CurrencyLedgerEntry`): USD, EUR, GBP, CAD, AUD, KES, GHS, ZAR, NGN.
   324→- **Virtual account** (Monnify Reserved Account): auto-provisioned on first wallet access.
   325→- **Funding methods**: card (Stripe Checkout), bank transfer (Monnify webhook), USSD, mobile money (country-aware: MTN MoMo / M-Pesa / etc.), demo (sandbox simulate).
   326→- **Saved payment methods** (Stripe PaymentMethod + SetupIntent).

   416→### Security
   417→- **Rate limiting** (`rate-limit.ts`): Redis-backed sliding window (sorted set), in-memory Map fallback. Per-IP, per-user, per-identifier. RFC 6585 `Retry-After` header. Per-route config (login: 10/min/IP + 5/hour/identifier; register: 5/hour/IP; PIN attempts: 10/min/user).
   418→- **CSRF** (`csrf.ts` + `proxy.ts`): origin validation on POST/PUT/PATCH/DELETE to `/api/*`. Bearer tokens exempt. Webhook/cron exempt (use HMAC/secret).
   419→- **CSP** (per-request nonce via `proxy.ts`): `default-src 'self'`, `frame-ancestors 'self'`, `base-uri 'self'`, no `unsafe-inline` in production script-src.
   420→- **Security headers** (`security-headers.ts`): X-Frame-Options DENY (prod), X-Content-Type-Options nosniff, Referrer-Policy strict-origin-when-cross-origin, Permissions-Policy camera/mic/geolocation=(), HSTS 2-year preload.
   421→- **PII encryption** (`crypto.ts`): AES-256-GCM with versioned payloads (`v1:<base64>`), key rotation via `TURBOPAY_PII_KEY` + `TURBOPAY_PII_PREV_KEYS`. Fails closed in production if key missing.
   422→- **Scrypt password hashing** (16-byte salt, 64-byte key, `scrypt$salt$hash` format), timing-safe compare via `crypto.timingSafeEqual`, dummy-hash path to prevent user-enumeration timing attacks.
   423→- **PIN**: 4-digit, scrypt-hashed, 5-fail → 15-min lockout, weak-PIN blocklist.
   424→- **OTP**: CSPRNG (`crypto.randomInt(100000, 1000000)`), SHA-256 hashed at rest, 10-min TTL, single-use `verificationToken` for email links (so OTP never in URL).
   425→- **Audit log** (`AuditLog`): every auth/wallet/transfer/bill/kyc/aml/admin/webhook action logged with userId, action, category, severity, IP, UA, metadata (JSON). Indexed for queries.
   426→- **Device tracking** (`Device`): sha256(UA + /24 IP subnet) fingerprint, trusted flag, first/last seen.
   427→- **Security events timeline** (`SecurityEvent`): 12 event types (LOGIN_SUCCESS/FAILED, DEVICE_NEW/RECOGNIZED/TRUSTED/REVOKED, SESSION_REVOKED, PIN_CHANGED, PASSWORD_CHANGED, STEP_UP_REQUIRED/PASSED/FAILED).
   428→- **Idempotency** (`IdempotencyRecord`): all payment operations dedup by client-provided key.
   429→- **Webhook verification** (`webhooks/registry.ts`): HMAC-SHA256 signatures, DB-backed secrets, `crypto.timingSafeEqual`, demo-bypass hard-gated to non-production, replay protection (timestamp window), idempotent via `WebhookEvent` table keyed on `[provider, providerRef]`, dead-letter queue.
   430→- **Outbox pattern** (`OutboxEvent`): events written inside the same Prisma tx as state change, drained by `/api/cron/outbox-publisher` every minute. Eliminates dual-write window.
   431→- **Cron leader election** (`CronLock` + `acquireCronLock`): Postgres row lock with TTL — only one instance runs each cron at a time.
   432→- **SSRF guard** (`ssrf.ts`): blocks private IPs + hostname blocklist. Audit noted it doesn't resolve DNS (potential DNS-rebinding bypass — admin-gated only).
   433→- **Circuit breaker** (`circuit-breaker.ts`): Redis-backed distributed state, 5 consecutive failures → OPEN (30s cooldown), 2 successes in HALF_OPEN → CLOSED.
   434→
   435→### Notifications
